ファイル管理が適切に行われていない場合，重要な情報が散逸したり，錯綜したりするなどして問題やミスの温床となります．部屋を整理整頓するように，データも正しく整理しておくことが重要です．本章では，これらの基礎的な知識を概観するとともに，主に技術者向けに，ファイル管理に関する技術についても扱います．

フォルダ構造と命名規則

ファイル管理の事故の多くは，特別なトラブルではなく，「どこに何があるかわからない」「どれが最新版かわからない」といった状態から始まります．

（例）

  • 「関西俳句バトル2100-投句一覧-最新版-000101」
  • 「関西俳句バトル2100-投句一覧-最終版（校正済）」
  • 「関西俳句バトル2100-投句一覧-最終確定版」
  • 「最終更新-関西俳句バトル2100-投句一覧-本当の最終版」
  • 「関西俳句バトル2100-投句一覧-確定版2」
  • 「関西俳句バトル2100-投句一覧-本当の最終版-final」

これは個人の整理能力で解決できる問題ではなく，フォルダ構造や命名規則が決まっていないことが原因です．

このような事例を減らすには，統一されたルールを設けることが効果的です．また，ルールには，

  • 日付(YYYY-MM-DD)をファイル名に入れる
  • 「最新版」ではなく「版番号/日付」で管理する

などの対策を含めるとよいでしょう．

共有フォルダの権限

共有ドライブや共有フォルダは便利ですが，不適切な権限設計は誤編集や誤削除の温床となります．

基本方針：

  • 編集できる人は最小限にする
  • 閲覧専用の共有を用意する
  • むやみに「リンクを知っている人は全員」の共有設定にしない（第2章　情報リテラシ概論）

バックアップとバージョン履歴

ファイルは，削除や上書きによって簡単に失われます．これを防ぐためには，バックアップとバージョン履歴の考え方が重要です．多くのクラウドサービスには，

  • 過去の状態に戻す機能
  • 削除したファイルを復元する機能

が備わっています．また，それらの機能が「あることを知っている」だけでなく，実際に使える状態にしておくことも重要です．

ログ（記録）を残す発想

事故対応で重要なのは「誰が悪いか」より「何が起きたか」です．

ログの価値：

  • いつ何が変わったか分かる
  • どこまで影響したか切り分けられる
  • 再発防止策（仕組み）に繋げられる

ログが残る環境を選ぶことや，権限共有でログを壊さないことが重要です．

Gitの概念

ファイルを管理する上で，変更履歴をたどったり，また必要に応じて過去のバージョンに戻したりしたくなることがあります．また，複数人で作業をする場合に，最新版のファイルを毎回やり取りしたり，同時に編集したりすることは，取り違えや意図しない上書きの可能性などを考慮したときに望ましい状態とはいえません．こうした問題を解決するシステムとして，特にコーディングの分野で多く使われているのがGitです．

Gitはプログラマだけの道具ではありません．「履歴を残しながら変更を管理する」という考え方そのものが重要です．Gitの考え方には，次のような利点があります．

  • いつ，どのような変更をしたか記録できる
  • 過去の状態に戻すことができる
  • 複数人で同時に作業できる
  • 変更点（差分）が明確にわかる

これは文書や設定ファイルの管理にもそのまま応用できます．

Gitで管理してよいもの・いけないもの

Gitは強力ですが，何でも入れてよいわけではありません．

基本方針：

  • 入れてよい：公開しても問題ない文書，設定（Secretsを除く），手順書，テンプレ等
  • 入れてはいけない：個人情報，秘密情報(Secrets)，未公開の内部資料（公開前提でないもの）

「非公開リポジトリだから大丈夫」という判断は危険です．誤公開・権限設定ミス・スクリーンショット共有等で流出する遠因となるからです．

Gitの基本用語

Gitでは，「変更をどこに置き，誰が確認できる状態か」を区別して考えます．

置き場所

  • リポジトリ(repository / repo)：ファイルと変更履歴をまとめて保管する単位です．
  • ローカル(local)：自分のPC上にあるリポジトリです．作業中の変更は，まずここにあります．
  • リモート(remote)：GitHubなどにある共有用のリポジトリです．チームで共通に見る置き場です．

変更を履歴にする

  • 差分(diff)：どのファイルの，どの部分を変更したかを示す表示です．
  • コミット(commit)：関連する変更を「この目的で行った変更」として履歴に確定する単位です．
  • コミットメッセージ：その変更の理由や内容を示す短い説明です．後から履歴を読むための手がかりになります．

コミット前の変更は，まだ自分の作業途中です．コミットして初めて，変更を戻したり他者に説明したりしやすくなります．

本流と作業の分岐

  • main（メイン）：通常，正式な最新版として扱う本流のブランチ名です．
  • ブランチ(branch)：本流を壊さずに変更を試すための作業上の分岐です．
  • マージ(merge)：ブランチで行った変更を本流へ統合することです．

チームへ共有する操作

リモート ── clone / pull ──> ローカル ── push ──> リモート
  • クローン(clone)：共有リポジトリを自分のPCへ最初に複製し，作業を始めることです．
  • プル(pull)：共有場所の最新の変更を，自分のPCへ取り込むことです．
  • プッシュ(push)：自分のPCでコミットした変更を，共有場所へ送ることです．
  • プルリクエスト(PR / Pull Request)：ブランチの変更を本流へ取り込む前に，差分を見てもらいレビューを依頼する仕組みです．

Gitに入れないもの

  • .gitignore：一時ファイルや秘密情報を誤って追加しないために，Gitの管理対象から除外する設定です．

ただし，すでにコミットしたファイルを .gitignore に書いても，履歴から消えるわけではありません．.envなどの秘密情報を入れないための予防策であり，秘密情報を安全に保管する仕組みそのものではない点に注意します．

よくある誤解

  • 誤解：プッシュしたら，自動的に本流（main等）が書き換わる
    • 現実：通常は「PRでレビュー→マージ」まで進まない限り，本流は変わらない
  • 誤解：コミット＝公開
    • 現実：コミットはローカルでもできる．公開（共有）はプッシュしたときに起きる
  • 誤解：プル(pull)とプルリクエスト(PR)は同じ
    • 現実：プルは「リモート→ローカルに取り込む操作」，PRは「変更を取り込む前のレビュー依頼」

共同作業を安全にする見取り図

Gitの共同作業は，個々のコマンドを暗記するよりも，変更が「誰に見えているか」「どこまで戻せるか」を意識して捉えると事故が減ります．次の流れは，その状態を保つための代表例です．

  1. クローンして作業を開始する（最初の1回）
  2. 作業前にプルして最新にする（他人の変更を取り込む）
  3. ブランチを切って変更する（本流を直接いじらない）
  4. 変更をコミットして履歴に残す
  5. プッシュしてリモートへ共有する
  6. PRでレビューし，問題なければマージして本流に取り込む

「レビューできる」「いつでも戻せる」ことが，Gitの価値です．

Gitの特長

クラウド文書にも履歴機能はありますが，Gitは次が強いです．

  • 変更理由をコミット単位で残しやすい
  • 複数人の変更が衝突したときに，差分として整理できる
  • 誤変更を「どの変更で起きたか」まで追いやすい

文章や規約，設定，テンプレのように「少しずつ改訂されるもの」と相性が良いです．

共同作業で起きやすい事故と回避

事故は技術ではなく，運用の曖昧さから起きやすいです．

  • 本流（main等）に直接反映してしまう
    • 回避：ブランチ＋PR＋レビューを基本にする
  • 変更が混ざって，何をしたのか分からなくなる
    • 回避：コミットを小さくする（1コミット=1目的）

公開/非公開の確認

Gitの事故で多いのは「うっかり公開」です．

  • リポジトリが公開か非公開かを最初に確認する
  • 公開してよい情報だけを入れる（非公開でも同様）
  • 外部公開が必要な場合は，公開対象を選別した別リポジトリに分離する

Git運用で特に注意する点（実務）

Gitは強い一方で，次の事故が頻発します．

  • 認証情報（トークン，APIキー，パスワード）をコミットしてしまう
  • うっかり公開リポジトリにしてしまう
  • 「一度入った履歴」は完全消去が難しいことを知らない

基本方針：

  • “公開してよい情報”しかGitに置かない
  • 秘密情報(Secrets)はGitに入れない（環境変数や専用保管へ）
  • 公開/非公開の設定を最初に確認する

もし誤って秘密情報(Secrets)を入れてしまった場合は，削除コミットだけでは足りないことが多いので，第1章　フェイルセーフとインシデント対応 の手順で速やかに共有し，無効化/再発行を優先します．

.envファイルもGitに入れない

.envは，APIキー，データベース接続情報，パスワードなどを環境変数として読み込むためによく使われるファイルです．

しかし，ファイル名が.envであるだけで暗号化やアクセス制御が行われるわけではありません．

基本方針：

  • .envは原則として.gitignoreに指定する
  • 共有するときは，チャットやメールに貼らず，専用のSecrets管理機能を使う
  • リポジトリには値を空欄やダミーにした.env.exampleだけを置く
  • 誤ってコミットした場合は，削除だけでなくSecretsを無効化・再発行する

「秘密情報(Secrets)を入れてしまった」時の考え方

Secretsの事故では，次の誤解が多いです．

  • 誤解：「消せば大丈夫」

現実：

  • Gitは履歴が残るため，単にファイルを消しても“過去の履歴”に残り得る

そのため優先順位は，まず止血です．

  1. 当該Secretsを無効化・再発行する
  2. 影響範囲（どこで使っていたか）を確認する
  3. 必要なら履歴の除去を検討する（技術者が対応）

ここでも 第1章　フェイルセーフとインシデント対応 の原則（止血→共有→記録）が基本になります．

実務で意識すべきポイント

ファイル管理において重要なのは，高度な技術ではなく，次の点です．

  • 保存場所と命名規則を決める
  • クラウドの履歴・復元機能を活用する
  • ログが残る環境を利用する
  • 「履歴を残す」というGitの思想を取り入れる

これらを実践することで，誤削除や誤編集による事故の影響を大きく減らすことができます．

現実の事例：マネーフォワードのGitHub不正アクセス（2026年）

2026年，マネーフォワードグループが開発・システム管理に利用するGitHubへ第三者が不正アクセスし，ソースコードが閲覧・コピーされました．同社の調査では，サービス更新作業中に個人情報を含むファイルが本来の管理手順から外れ，誤ってGitHub上に保管されていたことも公表されています．

本番データベースや金融機関との連携に必要な認証情報への侵害は確認されませんでしたが，安全確認のため銀行口座連携機能が一時停止され，GitHub上の個人情報について対象者への連絡が行われました．

この事例から学ぶ点：

  • 非公開リポジトリでも，不正アクセスや権限侵害は起こり得る
  • ソースコード以外の作業用ファイルを，リポジトリへ混入させない
  • 個人情報やSecretsを検出する仕組みを，コミット前とGitHub側の両方に設ける
  • 事故時には，直接侵害された範囲だけでなく，関連機能を一時停止して安全確認する場合がある
  • 本番データベースの漏えいと，リポジトリ内ファイルの漏えいを区別して説明する

参考資料

  • マネーフォワード「GitHubへの不正アクセス発生および銀行口座連携機能の一時停止」
  • マネーフォワード「GitHubへの不正アクセスに関する調査結果のご報告（第四報）」

確認

  1. 中～大規模プロジェクトにおける，適切なファイル命名規則の例を示せ．
  2. 秘密情報を誤ってGitにコミットした場合，なぜ削除コミットだけでは不十分になり得るか．

確認の解答

解答・解説を開く

  1. たとえば20260718_事業名_文書種別_v01.docxのように，日付・案件名・文書種別・版を一定の順序で付けます．団体内で規則を統一し，最終版のような曖昧な名前を避けます．

  2. 削除コミットをしても，過去のコミット，クローン，フォーク等にSecretsが残り，取得・悪用され得るためです．まず無効化・再発行を行い，必要に応じて履歴の除去を検討します．
